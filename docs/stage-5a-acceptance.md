# Stage 5A MVP 實機驗收準備

開發基準 `10dd494`，整合 manifest 版本 `0.2.0`。Stage 5A 的驗證範圍為 HA 測試框架、TCP loopback、SQLite 與備份。下列現場項目保留給管理員另外授權的 Stage 5B。授權可按步驟、Gateway、站號與操作個別記錄。

## 安裝與啟動檢查

1. 記錄目標 HA Core 版本、Gateway 型號與韌體、兩站韌體及拓撲。確認同一匯流排只登記一筆 Gateway。
2. 建立包含 HA 設定的備份，另保留目前已安裝的整合目錄。此開發版本使用本機 checkout 的 `custom_components/soyal_access`，整個目錄放到 HA 設定目錄下相同路徑。設定目錄是 `configuration.yaml` 所在處。已使用 HACS 的測試實例也以本機檔案為本輪驗收依據。
3. 重啟 HA，到「設定 → 裝置與服務 → 新增整合」選擇 **SOYAL Access Control**。輸入現場指定端點、RAW TCP、站號清單 `1,2` 及核定的逾時和冷卻時間。安裝與初始驗收期間保持門鎖控制停用，並確認測試實例沒有會呼叫 SOYAL 控制服務的既有自動化。
4. 確認一個 Gateway Device、兩個站號 Device、各站 Button／Switch 與診斷實體已建立。檢視 `Unknown` 的常開狀態、最近保存事件與同步階段。短連線閒置時 TCP 感測器可顯示未連線。未有成功交易時，最近通訊時間可能尚無資料。
5. 重載並再次重啟，確認實體仍對應同一站號，保存資料與未決狀態仍在。測試解除載入後 API 應拒絕存取該 entry，再載入後可讀回 SQLite。以 HA 診斷與測試端的連線監測確認在啟動、重載、卸載期間無自動送出門控或刪除交易。
6. 若需退回，先停用控制、卸載整合並保留事件資料庫與未決資料，再依原版本支援的 schema 還原程式碼及配套備份。若版本只支援 schema v1，另行保存現有 v2 資料庫供審查。還原歷史備份時先停用同步並核對現場佇列，避免把舊備份的位置視為現況。

[HA 設定目錄](https://www.home-assistant.io/docs/configuration/) · [整合檔案結構](https://contributors.home-assistant.io/core/integrations/file-structure/)

## Step 1　唯讀 Gateway 通訊

現有 Config Flow 驗證格式並建立 entry，連通性須另外驗證。現有 HA 現場 transport 的 allowlist 是門控指令，FIFO 只允許 loopback，故唯讀現場驗收需另用管理員核准的 SOYAL 診斷工具，在同一匯流排的其他發送端停止交易後進行。

先確認 Gateway 為 RAW TCP，再逐站執行一筆已核准的非 Hosting 唯讀查詢，例如已驗證的 `0x21` 唯讀 I/O 查詢。核對封包長度、checksum、回應碼與來源站號，記錄逾時及異常。I/O 回應用於確認通訊，依現有驗收範圍解讀。全程保持 `0x18` 持續輪詢停用。

## Step 2　雙站門控檢查表

管理員授權與現場安全確認完成後，才在 HA 啟用控制。由現場人員逐筆確認目標站及實際門鎖，記錄 HA 交易結果和實體結果。先測脈衝並確認回到現場原本狀態，再測常開與解除常開。每次只執行表中一筆。逾時、錯站或實體結果不一致時停止，保留 `uncertain`、請現場人員按既有安全程序處理。TCP 重連不會清除未決狀態。

| 驗收項目 | 站 01 | 站 02 | 通過條件 |
| --- | --- | --- | --- |
| RAW TCP 唯讀回應 | ☐ | ☐ | 長度、checksum、來源正確 |
| 脈衝開門 | ☐ | ☐ | 指定門短暫開啟並回復，HA 回應與觀察一致 |
| 常開 | ☐ | ☐ | 指定門維持常開，記錄 HA 交易結果 |
| 解除常開 | ☐ | ☐ | 指定門回到原先管理狀態，記錄 HA 交易結果 |
| 診斷與狀態 | ☐ | ☐ | 通訊時間與結果更新，Switch 無可信回授時維持 Unknown |
| 事件與人員對照 | ☐ | ☐ | 以 Step 3 已知樣本核對事件時間、站號、類型與人員位址 |

記錄欄位包括時間與時區、操作者、站號、指令名稱、HA 結果、現場觀察、是否恢復原狀、證據位置及驗收人。設備位置須由現場觀察確認。

## Step 3　事件資料核對

1. 使用現場管理員核准的唯讀工具，各站以 `0x25` 讀取**最舊佇列頭**。記錄來源、控制器原始時間、人員位址、事件碼、接收時間與是否重讀同一筆。原始封包放在限權環境，驗收紀錄不附卡號或 PIN。
2. 核對可辨識的刷卡 `0x0B`、出門 `0x10` 與可產生的 PIN `0x1C`，以已知現場操作或經授權的既有紀錄作對照。某事件類型沒有出現在佇列頭時，標記為未驗證。新刷卡即使發生在讀取前，也可能位於 FIFO 尾端。維持 `backfill`，以控制器本地時間與 UTC 匯入時間分別核對。
3. 用現有管理員 WebSocket 查詢與本地人員對照核對兩站資料。以匿名化 fixture 或使用已驗證的歷史資料庫離線重播，確認 SQLite 保存、HA 重啟恢復及同地址的站別姓名。暫無 HA 現場 `0x25` 匯入入口，現場唯讀捕獲與本機保存驗證分別記錄。
4. 在獨立已知為空的控制器或自然為空且經管理員證明的佇列量測真實回應，必要時逐站及逐韌體記錄。缺乏獨立證據時，將 ACK、NACK、逾時或未知回應標記為未確認。等待空佇列驗收，不為製造空佇列移除事件。

## Step 4　單筆刪除前置條件

- ☐ 取得可驗證的完整事件備份，抽樣還原並保存站別筆數與佇列頭證據。單純重讀同一個 `0x25` 佇列頭無法建立完整備份，需經核准的獨立備份途徑。
- ☐ 已在相關韌體核對空佇列回應，並證明 Gateway 的遲到回應處理及恢復方式。以經驗證的排空條件或重置為準。
- ☐ 已在本機驗證 SQLite 保存、重啟後未決狀態、備份還原及檢查點不符時停止。
- ☐ 站 01 與站 02 各自有經審查的一次一筆程序、可識別的測試佇列頭及不同的下一筆、停止條件與證據紀錄。站 01 刪除行為仍待驗收。
- ☐ 管理員另行授權指定站號及單筆刪除。核對目標、已保存的原始佇列頭與持久化「可能已送出」記號後才可進入單筆驗收。只確認匹配 ACK 及不同的有效下一筆，遇到 ACK 遺失、相同佇列頭、NACK 或無法辨識便保留未決並停止。

目前部署版本把 `0x37` 限制於本機模擬器。前置條件的完成只代表可安排另行審查的現場單筆驗收。
